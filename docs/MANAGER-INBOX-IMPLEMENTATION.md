# Manager Inbox System — Implementation Complete

## Overview

A full manager inbox system has been implemented using the existing game event architecture. The inbox transforms `EventLogEntry` events into user-facing `InboxMessage` objects with categorization, prioritization, duplicate prevention, and persistence.

## Architecture

### Core Types (types.ts)

Added to GameState:
- `inbox?: InboxMessage[]` — array of manager messages
- `inboxSettings?: InboxSettings` — configuration (archive threshold, dedup window)

New discriminated types:
- `InboxMessageCategory` — "transfers", "squad", "training", "scouting", "youth", "board", "matches", "world"
- `InboxMessagePriority` — "low", "normal", "high", "critical"
- `InboxMessageAction` — optional action the manager can take (view_player, view_transfer, etc.)

### Message Generation (inbox.ts)

**eventToMessages(event, state) → InboxMessage[]**
- Transforms EventLogEntry → InboxMessage
- Handles 10+ event types (TRANSFER_COMPLETED, YOUTH_GENERATED, PROMOTION, PLAYER_RETIRED, MATCH_PLAYED, etc.)
- Applies context-aware content:
  - Different titles/priorities for manager's club vs. other clubs
  - High priority for manager's team events
  - Critical priority for promotions/relegations/competition wins
  - Includes entity IDs for linking to related screens

**isDuplicateMessage(msg, existing, dedupeWindowDays) → boolean**
- Prevents duplicate messages within a time window
- Deduplicates by title + category + relatedEntityId
- Ignores archived messages
- Configurable dedup window (default: 1 day)

**generateInboxMessagesFromEvents(state, lookbackDays) → InboxMessage[]**
- Scans recent events (within lookback window)
- Filters out events already processed (sourceEventId check)
- Generates messages via eventToMessages()
- Applies duplicate prevention

**cleanupInbox(state) → GameState**
- Archives messages older than archiveOldAfterDays (default: 30)
- Removes permanently deleted messages older than archive threshold + 10 days
- Preserves recent history while bounding array size

**getUnreadCount(state) → number**
- Counts unread, non-archived messages
- Used by UI for badge display

### Reducer Integration (reducer.ts)

Three new GameAction types:

**MARK_INBOX_MESSAGE_READ**
- Toggles isRead status on a message
- Updates state.inbox in place

**DELETE_INBOX_MESSAGE**
- Removes message from inbox array
- Permanent deletion

**GENERATE_INBOX_MESSAGES**
- Manual dispatch to process recent events
- Optional lookbackDays parameter (default: 1)
- Generates messages and runs cleanup

### Daily Hook System (inbox.ts)

Registered on the "events" hook:
```typescript
registerDailyHook("events", (state, time) => {
  const newMessages = generateInboxMessagesFromEvents(state, 1);
  let nextState = {
    ...state,
    inbox: [...(state.inbox ?? []), ...newMessages],
  };
  return cleanupInbox(nextState);
});
```

Runs automatically every day after events have been generated by other systems. Ensures:
- Messages are only generated from events up to 1 day old
- Duplicates are never created
- Old messages are archived on schedule

## Supported Event Types

The system transforms the following EventLogEntry types into inbox messages:

1. **TRANSFER_COMPLETED** → transfers (high priority for recipient club)
2. **TRANSFER_REJECTED** → transfers (normal priority)
3. **TRANSFER_ACCEPTED** → transfers (high priority)
4. negotiation_started → transfers (normal)
5. negotiation_rejected → transfers (normal)
6. **MATCH_PLAYED** → matches (high for manager's team, normal for others)
7. **PLAYER_RETIRED** → squad (high priority if club player)
8. **PLAYER_MOVEMENT** → squad (high/critical for high-severity issues)
9. **YOUTH_GENERATED** → youth (high if high potential, normal otherwise)
10. **PROMOTION** → world (critical priority for manager's club)
11. **RELEGATION** → world (critical priority for manager's club)
12. **COMPETITION_WINNER** → world (critical priority for manager's club)
13. **MANAGER_OBJECTIVE** → board (high if failed, normal if achieved)

Other event types (PLAYER_CREATED, EUROPEAN_QUALIFICATION, MANAGER_APPOINTED, MANAGER_SACKED) are tracked in events but don't generate inbox messages.

## Data Flow

```
GameState.events[] (EventLogEntry[])
    ↓
runDailyTick() @ daily hook "events"
    ↓
generateInboxMessagesFromEvents()
    ├→ Filter recent events
    ├→ For each event: eventToMessages() → InboxMessage[]
    ├→ Deduplicate via isDuplicateMessage()
    └→ Append to state.inbox
    ↓
cleanupInbox()
    ├→ Archive messages older than 30 days
    └→ Remove permanently deleted messages
    ↓
GameState.inbox (InboxMessage[])
    ↓
UI: routes/inbox.tsx
    ├→ Filter by category/archive status
    ├→ Dispatch MARK_INBOX_MESSAGE_READ
    └→ Dispatch DELETE_INBOX_MESSAGE
```

## Design Decisions

**Why Messages Transform Events Rather Than Mirror Them:**
- Events are authoritative game facts (what happened)
- Messages are player-facing communication (why it matters)
- Keeps event system pure, allows inbox to be context-aware

**Why Daily Hook Instead of On-Demand:**
- Consistent with other reactive systems (training, injuries, etc.)
- Prevents duplicate message generation on multiple state reads
- Ensures messages are generated in proper sequence

**Why Deduplication Window Instead of Exact ID Matching:**
- Duplicate events can exist (system bugs, resimulations)
- Manager cares about unique situations, not unique database records
- Window allows same player's repeated injuries to generate messages

**Why Archive Instead of Delete:**
- Preserves history without unbounded array growth
- Allows recovery of archived messages
- Can implement "restore" feature later

## Performance

- Message generation: O(n) where n = events since last inbox update (typically 1-7 events/day)
- Dedup check: O(m) where m = existing messages (typically 50-200)
- Total daily overhead: <1ms per day advanced
